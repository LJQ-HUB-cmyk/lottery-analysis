### 二、根因总结

#### 直接原因

`daily_review.py` 内部的多策略 loop 包含了一个不存在的策略名 `auto_tuned`，导致 `compare_result.py` 报错（exit=2）。

#### 连锁效应

```
auto_tuned 不存在
  → compare_result.py exit=2
    → daily_review.py exit=2（有失败步骤）
      → lottery_review_job.py L280: if not daily_ok → True
        → sys.exit(2)（直接退出）
          → hermes_push.py 根本没有被调用
            → 用户收到的只有"脚本以代码2退出"
```

#### 逻辑缺陷

`lottery_review_job.py` L279-286 的判断过于激进：

```python
# ── Step 5: 目标彩种齐全 → 正常复盘 ──
if not daily_ok:                           # ← exit_code=2 → True
    status["status"] = ERROR
    status["reason"] = "daily_review.py 执行异常"
    sys.exit(2)                            # ← 直接退出，hermes_push 没机会跑
```

- `daily_review.py` 失败（exit=2）**不等于复盘数据不可用**
- 实际上 default/conservative/diversity 三策略的 `compare_latest.json` 已成功生成
- `check_lottery_ready()` 返回的是 True（因为 compare 文件存在且内容正确）
- 但 `if not daily_ok` 先于 hermes_push 被检查，导致本应走通的路径被截断

#### 错误的错误描述

日志中 `[ERROR] daily_review.py 执行异常` 是不准确的：
- daily_review.py 正常跑完了全部流程（拉取、特征、三策略对比、摘要）
- 只是在最后的 auto_tuned 这一步报错了
- 核心复盘数据（26135=939 / 2026135=487）已正确写入 CSV 和 JSON

---

### 三、修复方案

#### 方案 A：移除 `auto_tuned` 死策略（推荐，与方案 B 同时实施）

在 `daily_review.py` 中移除策略列表中的 `"auto_tuned"` 项。

**优点**：彻底消灭根源，即使方案 B 没到位也不会出同样问题。

#### 方案 B：`lottery_review_job.py` 加宽松判断（推荐，与方案 A 同时实施）

将 L279-286 改为：

```python
# 改为：如果 daily_review 报错但 compare 文件已就绪，仍继续
if not daily_ok:
    all_ready = all(check_lottery_ready(k, start_ts)[0] for k in targets)
    if all_ready:
        print(f"[WARN] daily_review 有失败步骤，但 {targets} compare 已就绪，继续推送", file=sys.stderr)
    else:
        status["status"] = ERROR
        status["ok"] = False
        status["reason"] = f"daily_review.py 执行异常，且 {targets} compare 未就绪"
        print(f"[ERROR] {status['reason']}", file=sys.stderr)
        write(task_name, status)
        sys.exit(2)
```

**优点**：任何 future 的部分失败场景（某个子步骤报错但主数据已生成）都不会再被一刀切拦截。

#### 方案 C：仅改 `lottery_review_job.py` 不修 daily_review

如果 auto_tuned 以后还有别的用途（如回测），只改 job 的判断逻辑。

### 四、其他发现

#### 数据源状态期号偏差


显示的是 26134 期（旧），而实际已拉取到 26135=939。原因是 `source_health.json` 是 14:35 生成的静态缓存，到晚间复盘时没有刷新。不过这不是本次推送失败的原因（推送根本没到 hermes_push 那一步），且这个设计是已知的（晚间复盘前应该刷新 source_health，参见 SKILL.md 中的 pitfalls）。
