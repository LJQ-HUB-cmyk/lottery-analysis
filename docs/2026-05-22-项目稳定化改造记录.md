## 三、改造方案概述

### 目标架构

```
Hermes / cron            → 定时触发
scripts/push/*.sh        → 薄入口：切目录、加锁、日志、启动 Python（~30行/个）
scripts/jobs/*.py        → 业务编排：拉取、预测/复盘、状态判断、去重
scripts/hermes_push.py   → 推送内容生成 + 去重 + 发送
output/status/*.json     → 每次任务的状态记录
```

### 统一规范

| 规范 | 内容 |
|------|------|
| 退出码 | 0=正常(含等待开奖/已推送跳过)，2=业务异常(阻断推送)，3=环境异常(venv缺失) |
| 去重键 | `review:date:pls-issue:d3-issue` / `kl8_review:issue` / `predict:date:...` |
| 状态枚举 | ready / pushed / skipped_waiting / skipped_already_sent / error |
| Shell 原则 | 不判断开奖、不判断期号、不判断是否推送 — 全部交给 Python |

```python
           and item.get("hash") == h and item.get("ok"):
```

**修改后：**
```python
# 新增：业务键去重（不受文本微小变化影响）
def already_sent_by_key(kind: str, dedup_key: str) -> bool:
    for line in ...:
        if (item.get("date") == today
                and item.get("kind") == kind
                and item.get("dedup_key") == dedup_key  # ← 按期号判断
                and item.get("ok")):
            return True
    return False

def append_log(kind: str, h: str, ok: bool, detail: str = "",
              dedup_key: str = ""):
    item = {
        "kind": kind,
        "hash": h,
        "dedup_key": dedup_key,  # ← 新增字段
        ...
    }

# 新增 CLI 参数
parser.add_argument("--dedup-key", default="",
                    help="业务去重键（job 层计算后传入，优先级高于自动计算）")

# 去重逻辑：业务键优先，hash 兜底
if not force:
    if dedup_key and already_sent_by_key(kind, dedup_key):
```

## 八点五、第二轮修复（GPT 审查后，同日 20:52）

> GPT 重新审查 GitHub 后指出 4 个工程问题。本轮修复 commit：`0d5293c`

### 8.5.1 shell set -e 导致异常时日志不完整

**问题：** `set -Eeuo pipefail` 下 Python 返回非 0 时 bash 直接退出，跳过 `EXIT_CODE=$?` 和 `end` 日志写入。

**修复后（4 个 shell 全部改为）：**
```bash
set +e
.venv/bin/python scripts/jobs/xxx.py 2>> "$LOG_FILE"
EXIT_CODE=$?
set -e
```

### 8.5.2 lottery_review_job.py final 兜底用了 --force

**问题：** `--force` 绕过去重保护，手动重跑或重复触发时会重复推送。

**修复后：**
```python
# 旧：--dedup-key ... --stdout --force
# 新：--dedup-key ... --final-check --stdout
result = subprocess.run(
    [PY, "scripts/hermes_push.py", "--mode", "review",
     "--dedup-key", status["dedup_key"], "--final-check", "--stdout"],
    ...)
```

> `--final-check` 让 hermes_push 在数据未齐时自动生成兜底通知，同时正常走 dedup_key 去重。

### 8.5.3 Job 过程日志混入 stdout

**问题：** 4 个 job 的 `print()` 进度日志（"执行中""成功/失败""跳过"等）直接写 stdout，会被 Hermes 当推送内容发出。

**修复后：** 全部过程日志改为 `print(..., file=sys.stderr)`，只保留 `print(stdout_text)` 在 stdout。

### 8.5.4 文件换行格式可能异常

**修复：** 新建 `.gitattributes`，强制所有文本文件 LF 换行。

### 8.5.5 README 补正式入口章节

新增"正式运行入口"章节，明确 cron 只跑 shell → Job → 业务逻辑。



### 8.6.1 emoji → 纯文本（Windows 兼容）

**问题：** 代码日志中的 emoji（✅⚠️❌）在 Windows GBK 控制台触发 UnicodeEncodeError，导致子进程崩溃。

**修复：** 6 个文件的代码日志 emoji 全部改为 `[OK]`/`[WARN]`/`[ERR]`。推送消息中的 emoji 保留（手机/飞书正常渲染）。

### 8.6.2 subprocess 强制 UTF-8 环境变量

**问题：** Windows 下子进程（feature_engine/compare_result/review_summary）继承系统 GBK 编码，emoji 崩溃。

**修复：** 6 个文件的 `subprocess.run()` 统一加：
```python
env = os.environ.copy()
env.setdefault("PYTHONUTF8", "1")
env.setdefault("PYTHONIOENCODING", "utf-8")
result = subprocess.run(..., env=env)
```

## 十一、关键设计决策

1. **Shell 保留但瘦身** — 不是去掉脚本，而是把脚本从"半个业务系统"降级为"纯启动器"
2. **Python job 统一编排** — 所有判断（开奖是否齐全、是否该推送、期号是否正确）都在 Python 层
3. **业务键去重** — 不靠文本 hash，靠期号。同一期只推一次，文本微变不会绕过
4. **退出码严格区分** — 等待开奖是正常行为(exit 0)，不是错误。只有脚本崩溃、数据损坏才算错误(exit 2)
5. **状态可追踪** — 每次任务落 `output/status/*.json`，排查问题不再靠 grep 日志猜测
6. **不改算法层** — 本次只改编排/容错/去重，不碰预测评分逻辑
